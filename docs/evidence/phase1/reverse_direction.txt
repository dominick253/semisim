Drag/brake path (the brief asks what they do today):
- Coast drag/rolling resistance (`_apply_coast_forces`,
  combination_controller.gd:778) applies `-v.normalized() * resist` to each
  body -> opposes velocity regardless of direction -> already correct in
  reverse, untouched.
- Service brakes use `motion = signf(v_forward_wheel)` (combination_controller.

- Engine braking (`engine_nm = -TireModel.engine_brake_torque_nm(engine_rpm)`,

  contact force in the -heading direction -- the same direction as the backward
  travel: the "brake" was accelerating the backup. Post-fix the sign flip makes
  it +heading, opposing the travel (measured +3470.3 Nm at 1 m/s backward,
  pre-fix -3470.3 Nm).

## The fix (shape 1 of the brief's two options)

`_drive_wheel_torque` sign-flips the finished drive-wheel torque when the
selected gear is reverse; `ratio()` stays a magnitude:

    var torque: float = DrivelineModel.wheel_torque_nm(
        engine_nm, throttle, ratio, 1.0 - _clutch_engagement(),
        _drive_forward_speed()
    )
    if transmission.gear == -1:
        torque = -torque  # AS4o (D59): gear R drives against the heading
    return torque

Why shape 1 over shape 2 (negative `ratio_for(-1)`): the consumers above show
the negative-ratio route would have changed the rpm path's `ratio <= 0.0 ->
idle` branch (a combination moving in reverse would read idle rpm) and
`speed_at_idle(-1)` (0.0), i.e. two silent behaviour changes beyond the
direction itself, versus a 3-line, one-call-site change here. The saturated-
branch wheel integrator and the mu-slip `braking` predicate
(`demand_n * v_forward_wheel < 0`) both key off the torque/demand sign, so they
are correct in reverse with the flipped torque (the reverse run never
saturates; grip-branch omega = v/r is negative as expected).
